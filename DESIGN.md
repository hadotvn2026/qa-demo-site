## Problem Statement

QA automation engineers learning Selenium and Playwright need a public site to practice against tricky DOM elements: authentication forms, dropdowns, checkboxes, hyperlinks, tables, file upload, file download, horizontal sliders, scroll, lazy loading, drag-and-drop, hover, context-click (right-click), and random popups. The existing options (the-internet.herokuapp.com, uitestingplayground.com, demoqa.com) cover the elements but look dated, are ad-cluttered, or feel like they were last loved in 2014. The site exists; the polished site does not.

## What Makes This Cool

The differentiator is taste, not features. shadcn/ui + Tailwind + dark mode + a command palette puts the visual gap between this and the-internet.herokuapp.com somewhere around a decade. The user's exact framing ("the-internet looks like 2012, demoqa is cluttered with ads") is a designer's complaint dressed up as a technical project — leaning into that is the win.

The second-order win is shipping a `tests/` folder of reference Playwright + Selenium solutions kept green by GitHub Actions. The repo becomes the curriculum. People star it for the working tests, not the site. CI badge on the README ("14/14 passing on every commit") is a moat the incumbents do not have.

## Constraints

- **One developer, weekend cadence.** 4 weekends + 1 buffer (~5 weekends total) of part-time effort to ship v1, broken down as:
  - **W1** — repo + Vercel + scaffold + landing page + 3 hero pages (login, data table, file upload).
  - **W2** — remaining 11 element pages at 80% polish. Hero pages get Lighthouse a11y ≥ 90 (the other 11 only need "no blocking a11y errors").
  - **W3** — `/tests/playwright/` reference suite (TypeScript, `@playwright/test`) covering all 14 elements, plus GitHub Actions wiring against Vercel preview URL. Build a shared Page Object layer (`/tests/pages/*.ts`) — both suites reuse it.
  - **W4** — `/tests/selenium/` reference suite (TypeScript + `selenium-webdriver` + Mocha — same language as the site, reuses the W3 Page Object layer for all selectors). Chrome-only via `selenium-manager`. Firefox/Safari are v1.1. Selenium is a v1 ship gate; if it slips, launch slips.
  - **W5 (buffer)** — README polish, GIF/video capture, custom domain, deploy-to-Vercel button config (`vercel.json` template + repo settings), launch.
- **No real backend.** Use Next.js 15 API routes for upload echo, server-streamed CSV download generation, and stateless cookie-based auth (single hardcoded credential pair). No DB. No persistent users.
- **Free-tier hosting.** Vercel for the site, GitHub Actions for the test runner (free tier covers public repos indefinitely).
- **Public from day one.** The repo is the artifact — README and commit history matter.
- **All 14 elements ship in v1.** Breadth wins, polish per page is uneven but acceptable; the home page and 3 hero pages need to be screenshot-quality. "80% polish" on the other 11 means: dark mode works, no console errors, no blocking a11y errors (color contrast + alt text + semantic landmarks), no extra micro-animations. Lighthouse a11y ≥ 90 is a gate only for the hero pages.
- **Vietnamese-English bilingual is out of scope for v1** (raised as an option in D2; user picked the modern-UX angle instead). Can be added later via next-intl without touching the data model.

## Premises

1. **P1 — Modern UX alone is enough of a differentiator to launch on.** Polished site + dark mode + command palette beats the-internet.herokuapp.com for QA learners who would rather not screenshot a 2012 page in their own portfolio.
2. **P2 — Breadth (14 elements) beats depth (6 polished) for v1.** A Reddit r/QualityAssurance launch comment thread is brutal on missing features and forgiving of basic styling. Ship all 14, polish the hero pages.
3. **P3 — Minimal backend is fine.** Next.js API routes for upload echo / download generation / fake auth. No DB. No persistent users.
4. **P4 — Distribution is a solved problem.** Vercel free tier, public GitHub repo, custom domain (`flakelab.dev` or similar) for ~$12/yr.
5. **P5 — Portfolio framing matters.** The repo is also a CV artifact. README quality, deploy-your-own button, screenshots, and reference test suite all serve hiring managers as much as learners.

## Approaches Considered

### Approach A: Polished Clone (minimal viable)

Next.js 15 + shadcn/ui + Tailwind, 14 elements with basic polish, sidebar nav, command palette, dark mode, deployed to Vercel. README with screenshots. ~2 weekends. Cleanest, fastest. Downside: leaves the portfolio premise on the table — no test suite, so the repo's CV value is 50% of what it could be.

### Approach B: Polished Clone + Reference Test Suite (chosen)

Approach A plus a `tests/` folder with reference Playwright AND Selenium solutions for every element. Kept green by GitHub Actions. README links directly to specific test files. The repo IS the curriculum. 4 weekends + 1 buffer (W1–W5 in Constraints). The CI badge becomes the moat.

### Approach C: Practice Site as REPL (creative/lateral)

Approach B plus a "Run my test" side panel that executes user-pasted Playwright code in a sandboxed Vercel function or Fly worker. The site becomes a Playwright REPL. ~5–6 weekends MINIMUM, likely more once abuse mitigation is added. Cool, but introduces a remote-code-execution surface that side projects should not defend, plus per-execution hosting cost and abuse vectors. Not v1.

## Recommended Approach

**Approach B: Polished Clone + Reference Test Suite.**

Rationale: it is the lowest-cost / highest-leverage move on the table. The reference test suite directly serves P5 (portfolio framing), eats your own dogfood (P1 modern UX is hollow if your own tests fail on the site), and ships in the 4-weekends-plus-buffer plan in Constraints — still side-project scale, not "real product" scale. C is a real product, not a side project. A leaves the CV value on the table.

### Architecture sketch

- **Framework:** Next.js 15 (App Router) + TypeScript + React 19.
- **Styling:** Tailwind v3.4.x + `shadcn` CLI 2.x against the legacy v3 registry + `next-themes` for dark mode. (Tailwind v4 deferred to v1.1 — the early-2026 shadcn-canary v4 registry has rough edges around theming variables and `tw-animate-css` migration.)
- **Components by element:**
  - **Auth** → shadcn `Form` + a hand-rolled `/api/login` route that sets an HttpOnly signed cookie (`iron-session` v8 with `AUTH_SECRET` env var generated at first deploy). Hardcoded credential pair (`tomsmith` / `SuperSecretPassword!`, the-internet style). No signup, no DB, no `next-auth`. Lockout-after-3-failures: failure count is stored in the same signed session cookie; 30-second wall-clock auto-reset on the server; "Reset attempts" button on the page clears the count immediately. Per-session, not per-IP, so practice sessions never wedge.
  - **Dropdown** → shadcn `Select` + a second page with a custom `<div>`-based dropdown (no native `<select>`, no ARIA listbox role) for "tricky selector" practice.
  - **Checkboxes** → shadcn `Checkbox`, both controlled and uncontrolled variants. One checkbox is intentionally a styled `<div>` instead of `<input type=checkbox>` for the "click vs. JS click" gotcha.
  - **Hyperlink** → 5 explicit cases on one page: (1) same-tab internal link, (2) `target="_blank"` external with `rel="noopener noreferrer"`, (3) broken link that returns 404, (4) `mailto:` link, (5) anchor-jump to in-page section. Reference tests cover new-tab assertions explicitly.
  - **Table** → TanStack Table v8 with sort, filter, pagination, row-select. Hero page.
  - **File upload** → `react-dropzone` + Next.js API route that echoes filename, size, and MIME type. File contents are NOT persisted.
  - **File download** → API route at `/api/download/users.csv` that server-side generates a 100-row CSV of mock users on each request and streams it with `Content-Disposition: attachment`. Real network download, verifiable by tests.
  - **Slider** → `@radix-ui/react-slider` (already a shadcn dep). Single horizontal slider, 0–100, value displayed live.
  - **Scroll** → three cases on one page: (1) long-page scroll-spy nav, (2) "scroll into view" button targeting an off-screen element, (3) nested `overflow-y-auto` container that requires scrolling the inner div, not the page. Case 3 is the canonical Selenium gotcha.
  - **Lazy loading** → custom `useIntersectionObserver` hook (~15 lines) on top of the native `IntersectionObserver` API. No `react-intersection-observer` dependency (avoids React 19 peer-dep warnings).
  - **Drag-drop** → `@dnd-kit/core` + `@dnd-kit/sortable` + `@dnd-kit/utilities`. Sortable list of 5 items.
  - **Hover** → shadcn `HoverCard` over an avatar; reveals user details only on hover.
  - **Context click** → shadcn `ContextMenu` on a target div. Right-click reveals 3 actions.
  - **Random popup** → modal that fires after a randomized delay (default 5–15s). For deterministic test runs, the page accepts a `?popupDelay=0` query param that fires the modal immediately on mount; reference tests use this. Both behaviors documented in the page's "How to test this" tip.
- **Shell:** sidebar nav, landing page, `cmdk` command palette (Cmd-K to jump between elements), dark mode toggle, footer with GitHub link only (no RSS — there is no blog yet).
- **Tests directory:** `/tests/playwright/` (TypeScript, `@playwright/test`) and `/tests/selenium/` (TypeScript, `selenium-webdriver` + Mocha — same language as the site, runs Chrome only via `selenium-manager`). Both mirror the page structure; each element has at least one reference test. The reference suite uses the deterministic query-param overrides (`?popupDelay=0`, etc.) so tests never depend on randomness.
- **CI:** `.github/workflows/test.yml` runs two parallel jobs (`playwright`, `selenium`) on every push to `main` and on every PR from a branch in this repo. Both jobs use `amondnet/vercel-action@v25` (canonical, well-maintained) to wait for the preview deployment, then run against that URL. Selenium job pins `selenium-manager` for driver management to avoid chromedriver version drift. Status badges (one per suite) in README. **Caveat for fork PRs:** Vercel preview env vars are not exposed to forks for security reasons, so PRs from forks will skip CI; the suite re-runs on `main` after merge as the fallback gate.
- **Deploy:** Vercel free tier connected to the `main` branch; preview URLs auto-generated for PRs.

### Hero pages (the ones that need to be magazine-quality)

Three pages carry the "taste" claim. Polish budget concentrates here:

1. **Landing page** — single-screen, fits in one viewport. Information hierarchy:
   - **Eyebrow** (top, before headline): small-caps tracked label `14/14 PASSING · PLAYWRIGHT + SELENIUM` with a green dot indicator. This is the differentiator vs. the-internet/demoqa — it goes above the headline, not buried below the CTA.
   - **Headline** (anchor): "Practice the elements that break your tests." in chosen display font.
   - **Subhead**: one supporting sentence (rewrite to continue the headline's attitude — see Pass 4 finding on generic feature-list voice).
   - **Single primary CTA**: "Try the table page" as a solid filled button. The GitHub link is a small text link only (or in the top nav). Per P5, the goal is to get them impressed first, then they star the repo on the way out.
   - **14-element thumbnail strip** (below CTA, above the demo): a horizontal row of 14 small element name chips (Auth · Dropdown · Checkboxes · Hyperlink · Table · File upload · File download · Slider · Scroll · Lazy loading · Drag-drop · Hover · Context click · Random popup) with subtle hover states. Each chip is a link to that element page. Reveals breadth before commitment — addresses the "sidebar is a surprise" journey break.
   - **Live terminal animation as visual anchor** (replaces static video placeholder): a small terminal showing `playwright test` followed by 14 dots filling green and `14 passed in 2.3s`. Loops every ~8s. This kills the "70% whitespace, lacks live texture" feel AND breaks the centered-axis slop pattern (see Pass 4). The MP4 demo loop is downgraded to a secondary "Watch demo" link below the terminal.

   Sign-in success behavior: on successful login, redirect to `/elements/dropdown` (the next sidebar item) with a `SuccessToast` reading "Signed in. Try this one next." This solves cold read finding #16 (no auth hand-off).

   Departure / progress: out of v1. Localstorage progress tracking and "star the repo" nudges are deferred to v1.1.
2. **Data Table** — TanStack with everything wired up. The single page that is most visibly 2026 vs. 2012. Information hierarchy: page title (H1) → filter input + row-count → table (the practice surface, full visual weight) → pagination footer. The "How to test this" tip is NOT inline above the table — see "Tips drawer pattern" below.
3. **Login form** — clean shadcn form, real validation, server-side error states. The first page everyone tries because it is the first link in the sidebar. Information hierarchy: page title → tips drawer trigger → form card (single state at runtime — the wireframe's two-state side-by-side is a spec sheet, not the page).

### Tips drawer pattern (applies to ALL 14 element pages)

Every element page gets a vertical tab pinned to the right edge of the viewport, labeled `Selector →`. Click expands a panel showing one example Playwright/Selenium selector for that element + 1-2 sentences naming the specific gotcha (not generic teaching — peer-to-peer notes). Default state: collapsed. Position: fixed, right edge, vertically centered. Out of the way until summoned, available everywhere on the page, never cuts into the practice surface. This replaces the inline tip banner shown in the v0 wireframe.

Voice rule: NO "How to test this" / "Tip:" / "Note:" prefixes. Just the selector and one peer-voice sentence. The audience is a senior QA who is annoyed by 2012 sites — not a bootcamp learner needing tutorial scaffolding.

### Motion budget (v1)

Three intentional motions, nothing else. Each must respect `prefers-reduced-motion: reduce` (replace with no-op or static state).

1. **Live terminal animation on landing.** ~8s loop showing `playwright test` → 14 dots filling green sequentially (~120ms each) → `14 passed in 2.3s` → 1.5s hold → restart. ~150 lines of CSS keyframes OR Framer Motion sequence. THE visual anchor of the landing.
2. **Cmd-K palette open/close.** Slide-up + fade (180ms ease-out on open, 120ms ease-in on close). `cmdk` defaults are a hard cut — override with the `data-state` attribute hooks.
3. **Sidebar item hover + active.** Background fill transitions (100ms linear). Active item gets a 1px left-edge accent bar (emerald) that slides in on focus.

Hard cuts everywhere else: theme toggle, button press, modal enter/exit, page transitions, toast appearance. Cuteness costs trust on a tool site.

### AI slop guardrails (explicit DO NOT list)

These patterns are forbidden in v1. Any PR introducing one gets reverted:

1. **No 3-column feature grid** (icon-in-circle + bold title + 2-line description, repeated x3). The 14-element strip on the landing is a horizontal chip row, NOT a 3-column grid.
2. **No icon-in-colored-circle** decoration anywhere. Icons are flat line icons (lucide-react default), no background fill.
3. **No purple/violet/indigo gradients.** The accent is emerald. The background is near-black with at most a subtle radial gradient or dot grid (very low opacity).
4. **No centered-everything on the landing.** The headline + subhead + CTA cluster can be left-aligned in a max-1200px container; the live terminal animation goes top-right or right-rail to break the center axis.
5. **No decorative blobs, orbs, aurora, wavy SVG dividers.** The live terminal fills the visual space — that's the rule. If an engineer says "this hero feels empty," the answer is "make the terminal animation more prominent," NOT "add a blob."
6. **No emoji in nav, headings, or CTAs.** Emoji only as inline punctuation in body copy if it's load-bearing (rare).
7. **No bubbly border-radius.** All radii use `var(--radius)` (8px) consistently. Buttons, inputs, cards. Nothing bigger.
8. **No pure-black `bg-foreground` CTA.** Primary CTA uses `var(--color-accent)` emerald. Secondary actions are text links, not ghost buttons.
9. **No `system-ui` or `-apple-system` as the primary display/body font.** Geist Sans is the primary; system fonts are only fallbacks in the stack.
10. **No "Welcome to flakelab" / "Unlock the power of..." / "Your all-in-one solution" generic hero copy.** The headline + subhead are locked above.

### House-style state component family (`/components/state/`)

Five shared components that handle all loading, empty, error, success, and partial states across the entire site. Build once in W1, reuse everywhere. This is the discipline that prevents 14 pages from each shipping a different "no items found" string.

- **`<Skeleton>`** — pulse-animated rows for all loading states. Variants: `Skeleton.Row` (single text line), `Skeleton.Card` (block placeholder), `Skeleton.Table rows={N}` (table-shaped). Used for: Lazy loading initial render, Data Table while filtering, any `await` boundary.
- **`<EmptyState>`** — props: `icon` (small line icon, NOT a colored circle), `title`, `description` (one line), `action` (single primary button). Used for: filtered-empty Data Table, no-search-results in Cmd-K, Drag-drop with zero items, etc.
- **`<ErrorState>`** — inline (under-the-field) for form errors, full-block for page-level errors. Props: `severity` (error/warning), `message`, `recovery` (a "Reset" / "Try again" / "Reload" action). Red border using accent-red token, never raw `#FF0000`.
- **`<SuccessToast>`** — bottom-right transient toast for "File uploaded", "Download started", "Reset successful". Auto-dismiss 4s. Stack vertically if multiple.
- **`<ProgressBar>`** — for in-flight upload/download. Determinate when known, indeterminate (sliding bar) when unknown. Replaces any default browser file-picker loading affordance.

Copy voice for ALL state strings (one source of truth, no per-page drift): terse, sentence case, single period at the end. "No users match this filter." not "No results found!" — pick a voice and write a 5-line copy doc in the repo.

### Responsive & Accessibility specs (v1)

**Breakpoints:**
- `>= 1024px` — desktop default. Sidebar fixed left, content right.
- `768px–1023px` — tablet. Sidebar still visible but narrower (180px).
- `< 768px` — mobile. Sidebar collapses into a slide-in `Sheet` drawer triggered by a hamburger button in the top-bar.

**Per-element mobile behavior:**
- **Data Table** — horizontal scroll with sticky first column (Name) on narrow viewports. Filter input + pagination stack vertically below the table.
- **Drag-drop** — `@dnd-kit/core` includes `MouseSensor` by default; explicitly add `TouchSensor` for mobile + `KeyboardSensor` for accessibility. Sortable list works with finger drag, screen-reader announcements via `Announcements` API.
- **Hover, Context click** — these elements have no real mobile equivalent. Each page shows a small inline note: "Open on desktop to practice this gesture" — does NOT block interaction, just tells the user. Reference tests still run desktop-only.
- **File upload** — `react-dropzone` shows a tap-to-select fallback below the drop zone on touch devices.

**A11y rules (locked):**

1. **Touch targets ≥ 44×44px on mobile.** Override shadcn's 36px button height with a min-height util on mobile breakpoints. Sidebar items get 48px row height on mobile.
2. **Focus management.** On auth submit failure, focus moves to the FIRST invalid field (not the submit button). On modal open (random-popup), focus traps inside the modal; on close, focus returns to the trigger button. shadcn's Radix primitives handle this for free if used correctly — but the page-level forms need explicit `useFormStatus`/`useEffect` focus calls.
3. **Motion respects `prefers-reduced-motion: reduce`.** Live terminal animation freezes on `14 passed in 2.3s` (the final frame). Cmd-K palette open/close becomes a hard cut. Sidebar hover transitions become instant.
4. **Theme toggle a11y.** Button gets `aria-label="Toggle dark mode"` and `aria-pressed` reflecting current state. The visible icon (sun/moon) is `aria-hidden`.
5. **Skip-to-content link.** First focusable element on every page is a visually-hidden-until-focused "Skip to main content" link that jumps to `<main>`. shadcn does NOT include this — add it once in `app/layout.tsx`.
6. **Color contrast.** Body text (`var(--color-fg)` on `var(--color-bg)`) is 19:1 — passes AAA. Muted text (`var(--color-muted)` on `var(--color-bg)`) is 7.5:1 — passes AA. Verify any future copy never drops below 4.5:1 on body.
7. **Lighthouse a11y ≥ 90 enforced via CI.** `lighthouse-ci` step in `.github/workflows/test.yml` runs against the deployed Vercel preview URL on every PR. Targets: `/` (landing), `/elements/auth`, `/elements/table`. Fail the PR if any drop below 90.

## Reviewer Concerns
